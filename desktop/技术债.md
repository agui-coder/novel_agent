# Novel Agent Desktop 技术债分析报告

> 生成时间：2026-05-31 | 分析范围：Rust 后端 + React 前端 + Tauri 胶水层

---

## 一、致命级（Silent Data Corruption / 功能不可用）

### 1.1 `llm.rs` 流式工具调用缓冲区 Bug（`llm.rs:275-308`）

`chat_streaming` 中的 `tool_call_buffers` 将 **函数名和参数拼接在同一个字段**，导致每次工具调用都失败：

```rust
// 当前：entry.1 先被设为 name，然后 arguments 被 push_str 进去
if let Some(ref n) = f.name { entry.1 = n.clone(); }  // entry.1 = "get_file"
if let Some(ref a) = f.arguments { entry.1.push_str(a); }  // entry.1 = "get_file{\"file_name\":\"x\"}"
// ...
// 最终 name 和 arguments 都是同一个拼接后的字符串
ToolCall { ..., function: FunctionCall { name: args.clone(), arguments: args } }
```

**影响**：所有经过流式模式的 Agent 工具调用都会收到错误的函数名（因为 `name` 字段被 arguments 污染），工具执行必然失败。这是`run_agent_streaming` 的唯一调用路径（`agent.rs:98`）。

### 1.2 `lib.rs` 命令重复注册（`lib.rs:75-83`）

```rust
commands::style::style_init,       // 第 75 行
commands::rolling::rolling_state,  // 第 76 行
commands::import::import_preview,  // 第 77 行
commands::import::import_confirm,  // 第 78 行
commands::pipeline::run_pipeline,  // 第 79 行 ← 重复
commands::style::style_init,       // 第 80 行 ← 重复
commands::rolling::rolling_state,  // 第 81 行 ← 重复
commands::import::import_preview,  // 第 82 行 ← 重复
commands::import::import_confirm,  // 第 83 行 ← 重复
```

**影响**：Tauri 在注册重复 handler 时行为未定义。如果编译通过，调用 `deduce_stream` 等不会触发重复命令，但 `run_pipeline`/`style_init`/`rolling_state`/`import_*` 均有两条 handler，可能导致非预期行为。

### 1.3 会话系统完全是前端 localhost 假实现（`session.ts`）

```typescript
// 没有后端 API 调用，所有数据存在 localStorage
function loadAll(): StoredConversation[] {
    try { return JSON.parse(localStorage.getItem(STORAGE_KEY) || '[]'); } catch { return []; }
}
function saveAll(data: StoredConversation[]) { localStorage.setItem(STORAGE_KEY, JSON.stringify(data)); }
```

**影响**：
- 对话历史不持久化——切换电脑/清除浏览器数据后全部丢失
- 即使 RPC 调用成功触发了 AI 推理，对话记录不会以任何形式保存在服务端
- `archiveConversation` 和 `deleteConversation` 做的是完全相同的事（直接过滤掉）
- `activateConversation` 就是 `fetchConversationContext` 的别名，没有任何实际"激活"语义

### 1.4 前端的三个 API 函数返回假数据（`orchestration.ts:444-490`）

`fetchRollingWorkbenchState`、`buildRollingContinuationPayload`、`buildRollingOutlineHandoffPayload` 三个函数不发起任何网络/IPC 调用，直接返回硬编码的 stub 对象（所有字段为零值/空数组/空对象）。

**影响**：滚动续写视图（SandboxView）和流水线工作台若调用这些函数，会展示空白的假状态。

## 二、架构级问题

### 2.1 巨大的单体 Zustand Store（`store/index.ts` 948 行）

所有状态（书籍、文件内容、对话、Git 控制台、审阅、Draft、FSM）在一个 store 中。store 类型定义有 325 行（`store.d.ts`），包含 50+ 个 action。

**问题**：
- 任一字段更新都触发全量 selector 重计算
- AgentScope 隔离逻辑耦合在 store 内部（`chatMessagesByAgent`、`conversationByAgent` 等并行状态）
- 没有领域边界，修一个 UI 状态可能无意间触发 Git/审阅逻辑

### 2.2 同一"流式增量合并"模式重复 4 次（`store/index.ts`）

`appendAssistantDelta`、`appendAssistantReasoning`、`appendAssistantPreview`、`setAssistantStageProgress` 四个动作有几乎相同的结构：
1. 找最后一个事件
2. 如果 `status === 'streaming'` 且 label/source 匹配 → 合并
3. 否则标记上一个为 `done`，追加新事件
4. 用 `.slice(-11)` 截断

每个实现约 30-60 行，总共 ~200 行重复代码，差异只在字段名上。

### 2.3 后台 Rust 线程与前端 Tauri Event 之间的脆弱桥接

```rust
// ai.rs:47
let (tx, rx) = mpsc::channel::<agent::AgentEvent>();
std::thread::spawn(move || { for e in rx { app.emit("deduce:event", &e).ok(); } });
std::thread::spawn(move || {
    // 在另一个线程里做实际工作
});
```

**问题**：
- 如果 `app.emit` 失败（窗口关闭、JS 端未监听），错误被 `.ok()` 吞掉
- 没有背压机制——如果前端跟不上事件速度，事件丢失
- 取消逻辑使用全局 `HashMap<String, Arc<AtomicBool>>` 互斥锁保护
- `deduce_blocking` 在主线程中调用 `run_agent_streaming` 后循环读 channel，会阻塞 Tauri IPC 线程

### 2.4 Git 用作自动提交存储——每次 AI 写入都产生一次 git commit

每次 `draft_append`、`draft_replace`、`update_file` 等操作自动执行 `git_commit`。这意味着：
- 一次性 AI 多轮 tool call（最多 45 次迭代）会产生 **45 个 git commit**
- 提交信息固定为 `[AI_Update] draft append` 等无意义内容
- 真正的版本历史（作者的手动修改）被淹没
- `git log` 展示一堆无意义的自动提交

### 2.5 全局静态变量共享存储路径（`tools.rs:236-239`）

```rust
static STORAGE_ROOT: OnceLock<String> = OnceLock::new();
pub fn set_storage_root(path: &str) { STORAGE_ROOT.set(path.into()).ok(); }
fn get_storage_root() -> &'static str { STORAGE_ROOT.get().map(|s| s.as_str()).unwrap_or(".") }
```

引擎层的工具函数不通过参数接收 `storage_root`，而是依赖一个隐式的全局变量。如果忘记调用 `set_storage_root`（或多次调用），工具会在错误的路径上操作，且不会报错。

### 2.6 前端 App.tsx 达 3090 行

单个组件文件包含：顶层布局、路由、事件监听（Tauri event + custom DOM event）、全量 state 读写、所有 UI 行为的分发逻辑。这是整个项目最不可维护的文件。

## 三、可靠性 & 错误处理

### 3.1 错误类型为裸字符串

```rust
fn do_something() -> Result<(), String> { ... }
```

整个后端（~3000 行 Rust）**没有任何自定义 Error 类型**。所有错误传播用的是 `format!("...")` 字符串。这意味着：
- 调用方无法区分错误类型（`NOT_FOUND` vs `NETWORK_ERROR` vs `DATA_CORRUPTION`）
- 前端只能靠字符串包含匹配来判断错误码（`client.ts:90-99`）
- 无法实现精细化重试策略

### 3.2 普遍使用 `.unwrap_or_default()` / `.ok()` 吞错误

```rust
// tools.rs:293, 487
let mut files: Vec<_> = fs::read_dir(&chapters_dir).unwrap()...  // 读不到就直接 panic
// tools.rs:501
let dialogue_re = regex::Regex::new(r"...").unwrap_or(regex::Regex::new(r".").unwrap());
// llm.rs:128
let args: serde_json::Value = serde_json::from_str(&tc.function.arguments).unwrap_or(serde_json::json!({}));
```

总计超过 40 处这样的错误静默点。Rust 的 `Result` 语义被大量绕过。

### 3.3 Config 文件每次 LLM 调用都重新解析（`llm.rs:14-33`）

```rust
fn api_key() -> String { config_val("api_key").unwrap_or_default() }
fn api_base() -> String { config_val("api_base_url").unwrap_or_else(|| DEFAULT_BASE.into()) }
fn model() -> String { config_val("model").unwrap_or_else(|| DEFAULT_MODEL.into()) }
```

`chat_blocking` 和 `chat_streaming` 每次调用都会触发 `read_config()` → 从磁盘读文件 → `serde_json::from_str`。在一次 Agent 运行（最多 45 轮迭代）中，这意味着最多 **45 次磁盘 I/O** 来读同一个配置。

### 3.4 LLM 重试逻辑在解析错误上也重试（`llm.rs:158-216`）

```rust
for attempt in 0..=max_retries {
    // ...
    match resp.json::<ChatResponse>() {
        Ok(data) => { return Ok(...); }
        Err(e) => {
            last_err = format!("Parse error (attempt {}): {}", attempt + 1, e);
            if attempt < max_retries { continue; }  // 解析失败也重试！
        }
    }
}
```

如果 API 返回了格式错误但状态码 200 的响应，会重试 3 次。但重试不改变请求内容，同一个畸形响应会被解析失败 4 次。

### 3.5 工具调用结果的 etag JSON 字段名不一致

引擎工具返回 `etag`（小写），但前端 `get_file` 返回 `etag`，而 `get_markdown_outline` 也返回 `etag`。但 `archive.rs` 中 `read_file_or_virtual` 返回的变量叫 `etag`（Rust 端是 `etag_val`），类型是 `(String, String, bool, bool)`。多处不用结构体而用元组返回，调用方要记住元组位置对应哪个数据。

### 3.6 `git2` 错误用字符串匹配判断

```rust
// archive.rs:489-492
.map_err(|e| {
    if e.message().contains("nothing to commit") {
        return "".to_string(); // Map to empty string, losing error semantics
    }
    format!("Git commit error: {}", e)
})?;
```

这依赖 `git2` 的英文错误消息，在不同 locale 或 git2 版本下会失效。

## 四、数据一致性问题

### 4.1 文件写入不是原子的

所有文件操作都是直接覆盖写，没有 `write-temp + rename` 模式：

```rust
// archive.rs:286
fs::write(&file_path, &content).map_err(|e| format!("Write error: {}", e))?;
```

如果进程在 `fs::write` 中途崩溃，文件会损坏（半写）。

### 4.2 无并发保护

多个 Agent 推理线程可以同时执行：
- 没有文件级别的锁
- 没有书籍级别的互斥
- ETag 检查只在工具调用时生效，但两个并发推理可能在检查后同时写入

### 4.3 AI Agent 写入后再自动 git commit 的竞态

```rust
// tools.rs:353-354
fs::write(&file_path, &existing).map_err(|e| format!("Write: {}", e))?;
git_commit(&book_dir, &normalized_rel, "[AI_Update] draft append")?;
```

如果 fs::write 成功但 git_commit 失败（如 repo 被外部进程锁），文件内容和 git 状态不一致。

### 4.4 `git_unstage` 的降级策略不透明（`git.rs:258-274`）

```rust
pub fn git_unstage(...) -> Result<(), String> {
    // ...
    if let Ok(head) = repo.head() {
        if let Ok(commit) = head.peel_to_commit() {
            if let Ok(tree) = commit.tree() {
                if tree.get_path(std::path::Path::new(&path)).is_ok() {
                    // 用 index.add_path 来 "取消暂存"，实际上不对
                    let mut idx = repo.index()...;
                    idx.add_path(std::path::Path::new(&path))...;
```

`git_unstage` 如果文件在 HEAD 中存在，实际操作是**重新 add 到 index**（用 HEAD 版本覆盖），但这只是恢复 staged 版本到 HEAD，而不是真正的 unstage。如果文件是新文件（不在 HEAD 中），函数静默不做任何事情。

## 五、性能问题

### 5.1 每次 LLM 请求都新建 reqwest Client（`llm.rs:163-166`）

```rust
let client = reqwest::blocking::Client::builder()
    .timeout(std::time::Duration::from_secs(120))
    .build()
    .map_err(|e| format!("Client build error: {}", e))?;
```

**影响**：每次 HTTP 请求重建 Client（包括连接池、TLS 配置）。在高迭代 Agent 场景下（45 轮），会创建 45+ 个 Client 实例。

### 5.2 流式 Agent 内部使用阻塞 HTTP 客户端（`llm.rs:235`）

```rust
pub fn chat_streaming(...) -> Result<Option<Vec<ToolCall>>, String> {
    // ...
    let client = reqwest::blocking::Client::builder()  // 阻塞客户端
```

这意味着虽然叫 "streaming"，但调用线程被完全阻塞直到流结束。依赖 `std::thread::spawn` 来避免阻塞主线程。

### 5.3 Style 诊断每次都重新读取全部源章节

```rust
// style.rs:40-46（run_diagnostics）
files.sort_by_key(|e| e.file_name());
for f in files.iter().rev().take(source_count) {
    if let Ok(c) = fs::read_to_string(f.path()) {
        source_text.push_str(&c);
        source_text.push_str("\n\n");
    }
}
```

每次调用 `style_init`（force_rebuild=true）都重新读取最多 30 章原文。style 诊断是纯正则/统计计算，不需要 LLM，但会消耗 I/O。

### 5.4 Pipeline 同步批处理无并发限制有效性

```rust
// pipeline.rs:91-117
let results: Arc<Mutex<Vec<(usize, String)>>> = Arc::new(Mutex::new(Vec::new()));
// ...
std::thread::scope(|scope| {
    for (batch_idx, batch_chunk) in chapters.chunks(MAX_BATCH_CHAPTERS).enumerate() {
        // 每个 batch 启动一个线程调用 LLM
    }
});
```

虽然有 `MAX_WORKERS = 4` 常量，但实际代码在 `for` 循环中对每个 batch（50 章一个 batch）无限制地 spawn 线程。如果有 500 章就有 10 个并发线程同时调用 LLM，而 `MAX_WORKERS` 完全未被引用。

### 5.5 前端 `App.tsx` 中无 memo 化

3000+ 行的 App 组件没有任何 `React.memo`、`useMemo` 或 `useCallback`。每次 store 更新都触发全树重渲染。虽然没有发现明显的性能问题页面，但这是潜在问题。

## 六、安全问题

### 6.1 API Key 明文存储在用户配置目录

```rust
// config.rs
fn config_path() -> std::path::PathBuf {
    let base = std::env::var("APPDATA").or_else(|_| std::env::var("HOME")).unwrap_or_default();
    Path::new(&base).join("novel-agent").join("config.json")
}
```

`config.json` 中的 `api_key` 字段以明文存储，无加密无权限保护。

### 6.2 Tauri CSP 配置过于宽松（`tauri.conf.json:24`）

```json
"csp": "default-src 'self'; connect-src 'self' http://127.0.0.1:* http://localhost:* ws://127.0.0.1:* ws://localhost:*; style-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; font-src 'self' https://cdn.jsdelivr.net; img-src 'self' data:"
```

`connect-src` 允许任意端口号的 localhost 连接，`style-src` 允许 `unsafe-inline`。在生产桌面应用中应更严格。

### 6.3 `import_confirm` 有不同的 book_id 生成逻辑

```rust
// import.rs:131-137
let id = book_id.unwrap_or_else(|| {
    use std::hash::{Hash, Hasher};
    let mut h = std::collections::hash_map::DefaultHasher::new();
    book_name.trim().to_lowercase().hash(&mut h);
    format!("{}_{:08x}", slug, h.finish())
});
```

与 `books.rs:30-34` 使用 SHA-256 生成 ID 不同，import 使用非加密的 `DefaultHasher`。同一本书名通过不同入口初始化会产生不同的 book_id。

### 6.4 Shell 权限过于宽松（`capabilities/default.json`）

```json
"permissions": [
    "shell:allow-execute",
    "shell:allow-spawn",
    "shell:allow-stdin-write",
    ...
]
```

允许前端 JS 任意执行 shell 命令。虽然有 Tauri 的 CSP 限制，但如果 XSS 发生，攻击面很大。

## 七、代码质量 & 可维护性

### 7.1 后端文件级重复

- `handle_append_draft`（`tools.rs:331-361`）、`do_append`（`draft.rs:24-39`）、`append_file`（`archive.rs:307-361`）三处实现了基本相同的 append+etag_check+git_commit 流程
- `handle_replace_draft`（`tools.rs:363-384`）、`draft_replace_section`（`draft.rs:53-68`）、`update_file`（`archive.rs:258-305`）三处实现了基本相同的 replace+etag_check+git_commit 流程

### 7.2 前端 store action 方法体过长

`finishAssistantMessage`（60 行）、`startAssistantMessage`（35 行）、`pushUserMessage`（35 行）。每个 action 都混合了数据转换、状态归一化、边界判断、多个子状态的同步更新。

### 7.3 硬编码的中文字符串散布全球

Store 中的活跃 Agent 路由逻辑：
```typescript
// agentKey.ts
if (normalized === 'chapter_draft.md') return 'continuation_agent';
```
后端 AI 路由逻辑：
```rust
// ai.rs:33-35
"chapter_draft.md" => if intent.contains("审核")||intent.contains("审查") {
    (AgentType::Review, ...)
} else { (AgentType::Continuation, ...) },
```

文件名/中文关键词散落在多处，修改一个文件名或关键词需要同步改 Rust 和 TypeScript。

### 7.4 未清理的 Python 迁移残留文件

- `PYTHON_CLEANUP_PLAN.md`
- `PYTHON_ELIMINATION_PLAN.md`
- `public/test.html`（测试页面）
- `src/test-entry.tsx`

### 7.5 无类型安全的 IPC 边界

```typescript
// orchestration.ts
const { taskId } = await invokeApi<{ taskId: string }>('deduce_stream', { ... });
```

Tauri `invoke` 在编译期不校验 Rust 命令签名与前端参数是否匹配。参数名拼写错误只能在运行时发现。

### 7.6 测试覆盖严重不足

- Rust 端：1 个测试文件（`unit_tests.rs`），但其中包含大量**重写实现**（非测试生产代码），如 `parse_cn_num`、`compute_etag`、`chapter_stats` 等在测试文件中重新实现而不是引用生产代码
- 前端：0 个测试文件，无 Jest/Vitest 配置
- `storage/mod.rs:122-172` 有一个测试模块但所有测试用临时目录，且 `setup_tmp` 函数在 `setup_tmp()` 和 `#[test]` 之间有损坏的语法
- `#[test]` 后紧跟另一个 `#[test]`（`storage/mod.rs:133-136`）——这是无效语法

### 7.7 Markdown 解析逻辑重复多份

- `archive.rs:372-456` 有完整的 `parse_markdown_outline`、`parse_heading`、`extract_section`
- `tools.rs:246-299` 有内联的标题解析用于 outline/section（和 archive 版略有不同）
- `rolling.rs:67-115` 有 `parse_chapter_cards`、`parse_written_chapters`
- `import.rs:54-99` 有 `scan_chapters`
- 测试文件 `unit_tests.rs` 中还有 `parse_outline`、`extract_section`、`parse_chapter_numbers`、`chapter_stats` 的独立实现

同一个 markdown 解析逻辑被实现了至少 6 次。

### 7.8 `git_log` 中空的 HEAD 检查逻辑不一致

```rust
// git.rs:33-36
if repo.head().is_err() {
    return Ok(GitLogResult { status: "success".into(), book_id: id, commits: vec![] });
}
revwalk.push_head()...;
```

先检查 HEAD 不存在就返回空，但之后 `push_head` 可能失败——说明有些边界条件漏掉了。

## 九、前端工程问题

### 9.1 两种 API 客户端范式共存

`src/api/client.ts` 同时暴露：
- `fetchApi<T>(endpoint, options)` — 基于 `fetch()` 的 HTTP 客户端（为 Python 后端设计）
- `invokeApi<T>(command, args)` — 基于 `@tauri-apps/api/core` 的 IPC 调用（为 Rust 后端设计）

`src/api/sse.ts` 使用 fetch + ReadableStream 手动解析 SSE（为 Python 后端设计），但现在的 Rust 后端通过 Tauri event 传递流数据，不走 HTTP SSE。

**影响**：SSE 解析代码（150 行）现已完全死代码，但被 `orchestration.ts` 间接引用。

### 9.2 `window.confirm` 和 `window.prompt` 用于关键操作

```typescript
// useAgentSession.ts:274
const title = window.prompt('输入新的会话标题', current?.title || '');
// useGitWorkbench.ts:299
const confirmed = window.confirm(`工作区有未提交变更...`);
```

在生产 Tauri 应用中应使用 `@tauri-apps/plugin-dialog` 的原生对话框。

### 9.3 Monaco Editor 作为依赖但可能未被充分使用

`package.json` 中有 `@monaco-editor/react`，体积 ~5MB minified。如果只在简单的 textarea 场景使用，这是巨大的浪费。

### 9.4 滥用 `any` 类型

```typescript
// client.ts:8
public data?: any
// sse.ts:5
data: any;
// orchestration.ts
handlers.onAck?: (payload: any) => void;
```

几乎所有流事件处理器的 payload 类型都是 `any`。
