## 一、剩余致命级（P0 — 功能不可用）

### 1.1 会话系统纯 localStorage 假实现（`src/api/session.ts`）

```typescript
// 数据全在浏览器 localStorage，不持久化
function loadAll(): StoredConversation[] {
    try { return JSON.parse(localStorage.getItem(STORAGE_KEY) || '[]'); } catch { return []; }
}
```

**影响**：换设备/清浏览器/重装应用后对话历史全部丢失。`archiveConversation` 和 `deleteConversation` 逻辑完全相同。

**建议**：引入 `rusqlite`（bundled），每书一个 `state.db`，实现 sessions + messages 两张表。

### 1.2 前端三个 API 函数返回假数据（`src/api/orchestration.ts:444-490`）

`fetchRollingWorkbenchState`、`buildRollingContinuationPayload`、`buildRollingOutlineHandoffPayload` 不发起任何 IPC 调用，直接返回全零值/空数组 stub。滚动续写视图调用它们会展示空白状态。

## 二、架构级问题（P1）

### 2.1 948 行单体 Zustand Store（`src/store/index.ts`）

50+ action 在一个 `create()` 中。新增状态应按 slice 模式拆分（`createChatSlice`、`createGitSlice`、`createDraftSlice`、`createSessionSlice`），在 `index.ts` 中组合。

### 2.2 `error.rs` 类型未在 commands/ 层使用

`LlmError` 和 `ToolError` 已定义（`src-tauri/src/error.rs`，52 行），但 `commands/` 层所有 Tauri 命令仍返回 `Result<T, String>`。应逐步迁移到具体 Error 类型。

### 2.3 三个超大 Hook 文件

| Hook | 行数 | 问题 |
|------|------|------|
| `useWorkbenchActions.ts` | 715 | 18+ return 函数，应拆为 per-domain hooks |
| `useChatStream.ts` | 695 | 单一 hook 处理全部流式事件 |
| `useGitWorkbench.ts` | 631 | diff 加载、分支操作、stage/commit 混合 |

### 2.4 `App.tsx` 中 4 组重复的 `useState<AsyncPipelineState>` 模式

`worldInitActionState`、`styleInitActionState`、`rollingActionState`、`postConfirmHandoffState` 结构完全相同，应抽取为 `useAsyncPipelineState` hook。

## 三、可靠性（P2）

### 3.1 `commands/tools.rs:293` 生产路径 `unwrap()`

```rust
let candidates: Vec<_> = std::fs::read_dir(&chapters_dir).unwrap()...
```

import.rs、style.rs 的同类问题已修复，此处遗漏。

### 3.2 36 处 `.unwrap()` 分布

- Mutex 锁：10 处（`lock().unwrap()` — 只在 poisoned 时 panic，极少发生）
- Regex 编译：13 处（静态模式，编译期等效安全）
- 测试：9 处（可接受）
- 上下文安全：3 处（archive.rs — 已检查 `is_some()`）
- **遗漏生产路径：1 处（tools.rs:293）**

### 3.3 文件写入非原子

直接 `fs::write` 覆盖写，无 `write-temp + rename`。进程崩溃可能产生半写文件。

### 3.4 `git_unstage` 语义错误（`commands/git.rs:258-274`）

当文件在 HEAD 中存在时，实际上用 `index.add_path` 重新 add HEAD 版本，而非真正的 unstage。
