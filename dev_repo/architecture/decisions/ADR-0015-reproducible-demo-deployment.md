# ADR-0015: Reproducible Demo Deployment

Date: 2026-05-16

## Status

Accepted.

## Context

The project is moving from "works on the original developer machine" to a demo that can be reproduced by a reviewer, interviewer, or future contributor. The runtime has three different kinds of truth:

- Repository code, docs, scripts, and frontend/backend source.
- Per-book workspaces under `novel_git_server/storage/<book_id>/`, each with its own Git history.
- Dify live runtime state: PostgreSQL rows plus plugin storage for apps, workflows, providers, credentials, and installed agent/model plugins.

The exported `dify_workflows/*.yml` files are useful evidence, but they are not enough to recreate a working Dify runtime. Earlier work also established a strict authorship boundary: Codex and local scripts may orchestrate or verify, but outline and prose must still be generated by the project Dify Agents through LoreGit tools.

## Decision

Create a deployment reproducibility layer with two supported modes:

1. Local Windows demo pack.
   - Wraps the existing `start_all.ps1` runtime.
   - Uses configurable paths for Dify compose, backend/frontend ports, and seed locations.
   - Verifies or restores Dify runtime from sanitized seed material.
   - Runs backend/frontend startup and LoreGit endpoint sync through the startup orchestrator.

2. Compose demo pack.
   - Provides a repository-owned compose entrypoint for backend, frontend, storage volume, and smoke checks.
   - Treats Dify as an explicit runtime dependency that must be restored or connected through documented configuration.
   - Keeps real book storage, backups, and secrets outside Git.

Both modes must prove the same project chain:

- Dify Service API can reach the Flask LoreGit tools.
- The backend health and frontend routes are reachable.
- A smoke run can validate routing without fabricating outline or prose locally.
- Generated outline/prose ownership remains with Dify Agents, not Codex scripts.

## Boundaries

- No API keys, model credentials, Dify secrets, private `.dify_backups`, or real `novel_git_server/storage/` data may be committed.
- Sanitized runtime seeds must exclude credentials and private books.
- `dify_workflows/*.yml` stays exported evidence unless a contract explicitly restores or syncs it into live Dify PostgreSQL.
- Deployment scripts may create demo books or demo storage only as test material.
- Deployment scripts must not write novel prose or outline content directly.

## Consequences

- Deployment becomes its own architecture node: `deployment-repro-pack`.
- `docs/DEPLOYMENT.md` becomes the human entrypoint for reproducible demo startup.
- Later implementation slices may add `deploy/demo/**`, `.env.example`, `docker-compose.demo.yml`, and smoke scripts under this node.
- Smoke tests must check runtime health and route ownership, not just process liveness.

## Verification

- Architecture JSON files parse.
- Deployment docs describe both supported modes and secret/runtime boundaries.
- Later slices must prove their commands with targeted smoke checks before claiming reproducibility.
